# CLAUDE.md — Quadro Café

Guidance for Claude Code sessions working in this repo. Read `docs/HANDOFF.md` and `docs/rai-template-escalable.md` for full historical context, and `memoria.md` for the running project log.

## What this is

A mobile-first web app for Quadro Café, a real coffee shop at 4ª Av. de Los Palos Grandes, Edif. Los Eucaliptos, Caracas. Built under RAI Agency, intended as the flagship case study for a replicable "finca interactiva" template (see `docs/rai-template-escalable.md`).

## Stack

- **Vite + React 18**, plain JS (no TypeScript), inline styles (no CSS framework/Tailwind)
- Icons: `lucide-react`
- Single-file component pattern: the entire app lives in `src/App.jsx` (mounted by `src/main.jsx`).
- Deploy: GitHub → **Cloudflare Workers Builds** (not Pages — see `wrangler.toml`, which serves `./dist` as static assets with SPA fallback). Auto-deploys on push to `main`; `README.md` documents the build-time env vars. Note `VITE_*` variables must exist in Cloudflare's *build* environment, not as Worker runtime bindings.
- `npm run dev` / `npm run build` / `npm run preview`

```
PALETAS.oscuro  — dark theme ported from the owner's redesign: ink #0B0F0D, panel #131A17,
                  mocoties #1E5C4A, latón #C9873A, nebulosa #5B2E8C, alien #7FE3C0
```

The `claro` palette above supersedes the earlier v3 tokens (`#1F4D3D`/`#EDE9E0`/`#B08B4F`) per the owner's "BRIEF DE EJECUCIÓN v2 (ALTA GAMA)" — those older values are preserved in `docs/HANDOFF.md` as history but are no longer current.

Every component reads colors via `useTheme()` (a `ThemeCtx` React context) — never hardcode a hex value in a component; add it to `PALETAS` if a new color is needed in both themes.

Typography: the real brand fonts now ship in `src/assets/fonts/` (protected folder — never overwrite them). **VIOLA** is the actual logo lettering (a unicase didone: high contrast, `a` and `A` share one outline) and drives display/headers — `.disp`, `.disp-xl`/`.disp-l`/`.disp-m`. **Nexa** (Light 300 / Bold 700) is the brand sans for body and labels (`.mono`/`.label`/`.micro` — uppercase, tracked; despite the class name `.mono` this is not monospace, kept for backwards compat with existing markup). `Fraunces` survives only for `.script` (the italic accent line in the Inicio hero) and as the last fallback in the display stack; it superseded Cormorant Garamond/Archivo/IBM Plex Mono in the v4 pass.

**Accents in VIOLA (fixed 2026-08-10)**: VIOLA has 76 glyphs and *no* accented vowels, `Ñ` or `Ü`, so `TRIÁNGULO`/`SIFÓN`/`CAFÉ` used to render the accented letter in Fraunces — a different typeface inside the same word. `font-size-adjust: from-font` and `text-transform: uppercase` matched the size and the case but never the letterform, which is what reads as broken. The fix is `'VIOLA Acentos'`, a derived font generated by `scripts/generar-acentos-viola.mjs` (`npm run fuente:acentos`) into `src/assets/fonts-derivados/`: each glyph is VIOLA's own base outline with an accent composed on top, same upem/cap-height/advance. It sits second in the `.disp*` stack so the browser only reaches it for the codepoints VIOLA lacks. It's ~2.8 KB and Vite inlines it as a data URI. Re-run the script only if VIOLA.otf or the accent drawing changes. Nexa already covers Spanish accents — nothing to do there.

**Marco Quadro (retired 2026-08-09)**: used to be a corner notch (`.quadro-frame` CSS class, `clip-path` cutting the bottom-right corner) applied to product/finca/lote cards, echoing the mountain-peak notch in the real logo. The owner asked to remove it everywhere — all cards now use plain, fully-rounded corners (`borderRadius` on all four corners, no `clip-path`, no `borderBottomRightRadius: 0` override). `.quadro-frame` no longer exists in the CSS; don't reintroduce it.

## Motion system (Sprint "Alta Gama", Fase 2 — 2026-08-17)

Design tokens for every animation added from this sprint onward, defined as CSS custom properties at the top of `buildCss()` in `App.jsx`:

```
--motion-fast   150ms   touch/micro-interaction — immediate tap feedback
--motion-base   300ms   content transition — view/state changes
--motion-slow   500ms   large elements — hero, featured entrances
--ease-out      cubic-bezier(.16,1,.3,1)   entrances (something appears)
--ease-in-out   cubic-bezier(.45,0,.15,1)  state transitions (something changes state)
--ease-spring   cubic-bezier(.34,1.56,.64,1)  subtle overshoot, for tactile elements (buttons, chips)
```

Three new utility classes consume them: `.mo-tap` (spring press feedback, `transform:scale(.94)` on `:active`), `.mo-enter`/`.mo-hero` (reuse the pre-existing `qc-rise` keyframe — same `translateY(16px)→0` — just with the new token durations/easing instead of a loose `cubic-bezier`). **First and so far only usage**: `ThemeToggle`'s button swapped `className="press"` → `className="mo-tap"` — verified in prod DevTools as `transform 0.15s cubic-bezier(0.34, 1.56, 0.64, 1)`, matches the tokens exactly.

**Deliberately additive, not a migration**: every pre-existing animation class (`.rise`, `.pop`, `.slide`, `.sheet`, `.press`, `.tapfx`, `.pulse`, `.bar`, `.drip`, `.steam`, all the `qc-*` keyframes) is untouched, byte-for-byte — nothing in Fincas, Elio, or any already-animated screen changed in this phase. Later sprint phases should reach for the new tokens on *new* animation work; migrating old classes to the token system is a separate, explicit decision, not implied by this phase landing.

**Framer Motion evaluated and rejected for this sprint** (owner asked for an explicit bundle-size call before approving any new animation library): `framer-motion` full import is 62KB gzip (Bundlephobia); even the reduced `LazyMotion`+`domAnimation` path, documented at ~19.6KB, was measured at ~43KB gzip in real Webpack/Rollup builds per a GitHub issue on the library's own repo (motiondivision/motion#1585) — the "small" numbers assume ideal tree-shaking that doesn't always hold. The sprint's actual needs (entrance/exit, subtle spring, crossfade, fill-on-scroll bars) are already covered by the CSS system above — `qc-bar{from{width:0}}` in particular is already the exact fill-on-scroll shape Fase 4 needs, it just needs an `IntersectionObserver` trigger. Bundle impact of the token system itself: **+1.14KB gzip** (77.39KB vs 76.25KB baseline — pure CSS/comments, no dependency added). Reconsider a real animation library only if a later phase needs shared-element/layout animations or drag, and measure the *actual* Vite/Rollup build before committing, not the library's documentation numbers.

Respects `prefers-reduced-motion` for free — the existing global rule (`@media (prefers-reduced-motion:reduce){*{animation-duration:.001s!important;transition-duration:.001s!important}}`) already zeroes out any `transition`/`animation` on the page, this system included, without needing to declare it again.

## Motion system — Fase 3 (Carta, 2026-08-17)

Seven pieces landed in `Menu`/`Carrito`/`QuadroCafe` (`App.jsx`), all built on the Fase 2 tokens, no new dependency:

- **Fly-to-cart**: `volarAlCarrito(desdeEl, haciaEl, color)` — a shared helper (lives with the other motion pieces, right before `Menu`) that spawns a small dot and animates it via the **Web Animations API** (`el.animate(...)`), not a static `@keyframes`, because the origin point is different on every tap (each product card's "+" button is in a different place) — a fixed CSS keyframe can't express that, WAAPI can compute the translate distance per call. Self-removes on `animationend`. Respects `prefers-reduced-motion` by early-returning (checked by hand — this isn't a CSS `transition`/`animation`, so the global reduced-motion rule doesn't cover it automatically).
- **Cart badge bounce + count-up**: `useRetriggerAnim(dep)` (shared hook, same location) retriggers a CSS animation class (`.mo-bounce`, `qc-badge-bounce` keyframe) on every dependency change *without* remounting the element — classic remove-class/force-reflow/re-add-class trick — specifically so the sibling `AnimatedNumber` inside it doesn't lose its tween state on every +1/-1. `AnimatedNumber({value, format})` tweens the displayed number over `--motion-base` via `requestAnimationFrame`; **only rounds to an integer when no `format` is given** (counts) — passing `format={money}` (prices) keeps the raw float during the tween and snaps to the exact final value on the last frame, otherwise a $4.50 count-up would round through integers and land on $5. Found and fixed this during testing before it shipped.
- **Category transition (slide + underline)**: the chip row measures the active chip's real `offsetLeft`/`offsetWidth` (via per-chip refs, `useLayoutEffect`) and positions an absolutely-placed indicator bar under it — the chip's own background crossfade comes for free from the pre-existing `.press{transition:background .2s}`, nothing new needed there. The content below (banner image + item cards) is wrapped in **one single `<div key={cat}>`** that remounts as an atomic unit on category change, `.slide` class doing the fade+shift.
  - **Bug found and fixed during testing, worth remembering**: the very first version had the category banner (`ResponsiveImg key={cat}`) and the item-list wrapper (`<div key={cat}>`) as two *separate* sibling elements, each with their own independent `key={cat}`. Reproduced reliably (confirmed in a **production build**, not just dev/StrictMode) that switching categories left stale `<picture>` elements stuck in the DOM as extra siblings instead of being replaced — after Filtrado→Espresso→Filtrado there were 3 stacked category banners instead of 1. Root cause not fully pinned down (didn't matter once fixed), but two independently-keyed siblings at the same JSX position was the trigger. Fix: **one shared key on one wrapper div** containing both the banner and the content — verified via direct DOM inspection (`document.querySelectorAll('picture').length === 1` after the same click sequence that used to produce 3) that this eliminates it entirely. If a future phase needs two independently-animated siblings that both depend on a changing value, prefer a single shared wrapper key over two separate ones until this is understood better.
- **Skeleton on category change**: `cambiando` state is set **synchronously in the same click handler that changes `cat`** (`cambiarCategoria`), not reactively in a `useEffect` watching `cat` — a second bug found in testing: setting it reactively meant React had already re-rendered the new category's real items for one frame *before* the effect flipped the skeleton on, causing a real-content flash before the skeleton appeared. Setting both in the same event batches them into the same render, so there's never a frame with the new `cat` and `cambiando` still false. 260ms duration, `.mo-skeleton` shimmer (new: `qc-shimmer` keyframe, uses the theme's own `C.line`/`C.surface` so it's correct in both themes automatically) — honest in the code comments that this is a deliberate transition, not real loading (`useCarta()` has everything in memory already, categories are a client-side filter).
- **Accordion ("Elegir finca y taza")**: replaced the old conditional-mount (`{open && (<div className="pop">...)}`, which caused an instant layout jump) with the CSS `grid-template-rows: 0fr → 1fr` trick — always mounted, `aria-hidden` when closed, animates height smoothly via `--motion-base`/`--ease-in-out` with zero JS measurement.
- **Tactile feedback (scale .96 + shadow)**: new `.mo-press` class, **not** a change to the shared `.press` (which Elio/Fincas/the rest of the app still use untouched) — applied only to Menu's own buttons (qty +/-, add, "Elegir finca y taza" toggle, taza swatches) and Carrito's own buttons it doesn't share with anything else.

Bundle: **78.68KB gzip** (was 77.39KB after Fase 2 → **+1.29KB** for all seven pieces, zero new dependencies). Tested in both themes via Chrome headless (light/dark screenshots, both clean).

## Motion system — Fase 4 (Inicio, 2026-08-17)

Cuatro piezas, todas dentro de `Inicio` (`App.jsx`) — **no se tocó** el widget "La taza también sabe" de Aula/Academia ni el botón "Simular vertido" de Laboratorio, aunque comparten nombre/concepto; son homónimos confirmados con el dueño como trabajo nuevo y separado (ver `memoria.md`).

- **Barras (Extracción/Cuerpo/Acidez) con fill-on-load, ahora también con re-fill al cambiar de ruta**: `.bar`/`qc-bar` (Fase 2) ya hacía fill-on-load — `@keyframes qc-bar{from{width:0}}` deja que el navegador construya el "to" implícito desde el `width` inline, así que la barra siempre nace en 0 y crece. Lo que le faltaba (anotado en `memoria.md` desde Fase 2) era el trigger para repetirlo cuando el valor cambia sin que el elemento se desmonte. `useRetriggerAnim` (compartido con el badge del carrito, Fase 3) se generalizó para aceptar un nombre de clase (`className = "mo-bounce"` por defecto, retrocompatible) y `Meter` ahora acepta un `triggerKey` opcional que lo usa sobre `.bar` en vez de `.mo-bounce`. Sin `triggerKey` (Fincas, Laboratorio) el comportamiento no cambia — su dependencia nunca varía, el hook nunca reacciona.
- **Taza por color (SVG, crossfade+bounce)**: indicador nuevo junto al tubo 3D del comparador de rutas — un mug SVG minimalista (`TazaColor`) cuyo color nace de `geo.efecto.cuerpo` **y** `geo.efecto.extraccion` interpolados entre `C.card` y `C.brandAlt` (`colorTaza`/`mezclarHex`, mismo espíritu que la fórmula ya aceptada del simulador: "un modelo razonable, no medido en laboratorio", no un dato de café inventado). El crossfade es una `transition: fill` de CSS sobre el mismo nodo (por eso vive **fuera** del `div key={geo.id}` que remonta el tubo — un remount no tiene "desde" que animar); el bounce usa `useRetriggerAnim(geo.id)` sin parámetro de clase (default `.mo-bounce`). Cuando el dueño pase fotos reales de taza, este es el único componente que se reemplaza.
  - **Bugfix (2026-08-17, commit `4b8c5cf`)**: Sifón y AeroPress Punto Central se veían casi del mismo color — `colorTaza` normalizaba `cuerpo` contra 0-100 fijo, pero el rango real en `GEOMETRIAS` nunca sale de 38-84, así que solo se usaba el 46% central del gradiente. Ahora `normalizar()` estira cada eje (`cuerpo`, `extraccion`) contra su propio min/max real en `GEOMETRIAS`, y el color final combina los dos (`cuerpo × .6 + extraccion × .4`) en vez de solo `cuerpo`. Sigue sin hardcodear ningún hex — los extremos siguen saliendo de `PALETAS`. Confirmado por el dueño en producción.
- **"Simular vertido" (Inicio) — trazo de agua en tiempo real**: botón nuevo en la tarjeta del comparador. Reusa el mecanismo que ya tenía `EspiralTubo3D` (su prop `prog` dibuja el tubo progresivamente) en vez de inventar una animación CSS paralela — así el trazo real y el 3D nunca se desincronizan. `prog` vive en `Inicio` (antes fijo en `1`), un `rAF` lo corre de 0 a 1 en 4200ms al tocar el botón (misma duración que el "Simular vertido" de Laboratorio, para no tener dos ritmos de vertido distintos en la misma app), y un `useEffect` sobre `geo` resetea `prog`/`corriendo` al cambiar de ruta. Respeta `prefers-reduced-motion` a mano (salta directo a `prog=1`, sin loop) porque es JS/rAF, no una `transition`/`animation` CSS que la regla global ya cubra.
- **Parallax sutil en el hero**: la capa del modelo 3D (`heroCapaRef`) se traslada `translateY(min(36, scrollTop × .2))px` sobre el scroll real de `.qc-scroll` (throttled a un frame con `rAF`, cero libs nuevas) — el titular no se mueve, solo el fondo. Respeta `prefers-reduced-motion` a mano por la misma razón que el punto anterior.

**Verificado**: `npm run build` en verde (mismo fallo conocido del apóstrofo, no relacionado). Con `npm run dev` + Chrome headless por CDP (driver propio vía WebSocket nativo de Node, sin dependencias — ver `memoria.md`): capturas confirmando el fill/re-fill de las 3 barras a mitad de animación, la taza cambiando de color al swap de ruta, el tubo dibujándose a mitad de "Vertiendo…", y el cálculo del parallax verificado por lectura directa del `transform` inline (`translateY(30px)` con `scrollTop=150`, exacto `150×.2`). Probado en ambos temas. Cero errores de consola.

## The 3D model (`public/models/espiral.glb`)

The cone of the real dripper — **one mesh, one PBR material, no spiral of its own**: the spiral in Lab/Inicio is procedural (`TubeGeometry` in `src/lib/espiral3d.jsx`), it never came from the model. Don't go looking for it in the file.

**Compressed since 2026-08-10: 6.88 MB → 395 KB** (17.8×) by `scripts/comprimir-espiral-glb.mjs` (`npm run modelo:comprimir`) — textures were the weight (5.85 MB of 2048² maps for something drawn at ≤460 physical px), not geometry. Now: 512² WebP + `EXT_meshopt_compression`. The uncompressed original is recoverable from git history.

Two consequences to respect:
- **The loader must call `setMeshoptDecoder`** — `EXT_meshopt_compression` is declared *required*, so without it the model doesn't load at all. Meshopt and not Draco on purpose: three.js's Draco decoder references its `.wasm`/`.js` via `new URL(..., import.meta.url)`, which Vite bundles as duplicated assets (~1 MB of dead weight the service worker then precaches); meshopt's decoder inlines its WASM in the module (~29 KB).
- **Re-running the script on the already-compressed file would re-encode it.** It's meant to run against the original.

Its material is genuinely dark (baseColor averages 31/255), which is why in the dark theme the Inicio hero tints it — see `PALETAS[].modelo` / `veloHero` and `tenirModelo()`. A `material.color` alone can't lighten it: in three.js that value *multiplies* the baseColor texture, so it can only darken; the tint works by dropping `map` and letting the color apply over white. The relief is unaffected — it lives in the normal map.
